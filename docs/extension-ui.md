# 拡張UIを作りやすくするガイド

作り始めるときに迷わず、AIと利用者が相談しやすくするための推奨・参照例です。**必須ルール、適合審査、全画面を同じ見た目にするための規則ではありません。** 用途、利用者の好み、既存の画面の意図を優先してください。色・文字・余白・レイアウト・フレームワークは自由に選べ、別の案にするための承認や例外申請は不要です。

以下の値は、指定がなく迷ったときの出発点です。本体の `web-ui/src/styles.css` や `ThemeSelect.tsx`、テンプレートを参考にし、役に立つ部分だけ使えます。

## 迷ったときの見た目の例

- neutralな面の例: ライトは背景 `#f7f6f3`、面 `#fff`、文字 `#37352f`、境界 `#d8d7d4`。ダークは `#202020`、`#191919`、`#efefed`、`#40403d`。この色へ合わせる必要はありません。
- 操作色は本体の青を参考にできます。文字・塗りボタンならライト `#155f9f`、ダーク `#8dc6f3` などが一例です。ブランド色や利用者の好きな色でも、背景と文字を読み分けられる組合せを選びます。通常文字4.5:1、操作境界・フォーカス3:1などのアクセシビリティ指標は、確認の目安になります。
- 文字はsystem sans-serifと日本語fallback、本文14〜16px・行高1.5〜1.75、画面名は20〜22px、本文内の見出しは24〜28pxと18〜20px程度から試せます。コードや数値の等幅表示も用途に応じて選べます。
- 余白は4px単位、外側はスマホ16px・PC24px程度、角丸6〜8px、薄い境界などが出発点です。情報密度や作業領域を優先して調整できます。
- hover・focus-visible・disabled・実行中・エラーが分かると操作しやすくなります。44px程度のタッチ操作領域、ラベル、補足、色以外の状態文も参考にしてください。

## ホーム・戻る・進むの考え方

おすすめの分担は、本体がxangi全体へのホーム・共通ナビゲーションを用意し、拡張が一覧・詳細・編集などの業務操作を持つ形です。独自ナビゲーションも用途に合わせて選べます。

- **xangiホーム**: 本体の `/`（通常はチャット）へ戻る操作です。拡張の「一覧へ」「このアプリのトップへ」と区別します。iframe内にxangiホームを置くなら、既知の本体URLと `target="_top"` 等を使い、本体をiframeの中へ重ねて開かないようにすると自然です。単体サーバーでは本体の接続先を推測せず、分かっているときだけ案内できます。
- **本体の戻る・進む**: ブラウザの標準履歴をたどります。iframe内のリンクや、拡張が記録したhash/pushStateの履歴も対象です。保存内容を取り消す機能や、URLに記録していないアプリ内部状態を戻す機能ではありません。
- **拡張内の戻る・閉じる**: 一覧へ戻る、ダイアログを閉じる、編集を終えるなど、意味が分かる名前と動作を選べます。未保存の入力がある場合は、保存・復元・離脱確認などから用途に合う方法を選びます。

現行本体は `history.back()` / `history.forward()` を使い、独自のURL履歴スタックは持ちません。Navigation APIの親画面の判定は子iframeの履歴を含まないため、拡張表示中はボタンを操作可能にしてブラウザへ判断を任せます。行き先がなければ移動しません。通常画面では取得できる履歴状態を使い、判定APIがないブラウザでは操作可能なままです。

本体は拡張のホームや戻るボタンをID・ラベルで探して削除しません。重複を減らしたい拡張は、下記の表示属性を使い、自分のCSS等で共通ホームを隠す方法を選べます。保存確認など独自の役割を持つボタンや、好みのナビゲーションは残せます。

## テーマ連動を使いたい場合の参考

現行の `ExtensionView` は同一originのiframe読込時と本体のテーマ変更時に、rootへ `data-xangi-embedded="true"`、解決済み `data-theme="light|dark"`、`color-scheme` を渡します。これは表示用のヒントで、認証や権限の情報ではありません。別originには適用できず、postMessage APIは提供していません。

本体に合わせたい場合は、同じoriginの `localStorage["xangi-theme"]`（`light` / `dark` / `system`）を参照する例も使えます。未設定なら端末設定、OSやstorage変更時に再適用、保存不可でも現在の画面を使える、という作り方が参考になります。設定はorigin単位で、別host・port・instance間の同期ではありません。独自の配色・設定方式や、テーマの影響を受けない映像・キャンバスも選べます。

既存の好みや設定は、見た目をそろえるために無断で上書きせず、利用者の意図を確認しながら扱います。

## 用途に合わせて選べるもの

記事・メール・タスクなら読みやすい幅と密度、エディタなら編集・比較ペイン、モニターなら数値・推移・単位・古いデータの説明を優先できます。端末のANSI色、リモート映像、アバターの透明・クロマキー背景、機器固有の表現を一般画面と同じ配色にする必要はありません。

## 確認の進め方の例

AIは利用者の希望、既存の画面、対象の資料から、今回の目的に合う構成を選びます。テンプレートは参照例であり、必須SDKや必須コンポーネントではありません。

画面を変えたときは、PC/スマホやライト/ダークなど対象に合う条件で、開く → 主操作 → 結果 → 戻るを試すと見落としを減らせます。ホームの行き先、拡張内外の戻る・進む、キーボード、長い内容、空・読込中・エラー、テーマの切替も役立つ確認項目です。確認した範囲と未確認の範囲を伝えれば、次の作業へつなげやすくなります。

補助参照: [DADSアクセシビリティ](https://design.digital.go.jp/dads/guidance/accessibility/)。外部デザインも選択の参考として使えます。

## 本体内の見え方を確認する

共通ナビを本体に任せる構成では、独自のホーム・戻る・進むを埋め込み内へ重ねず、一覧・設定などの業務操作を残すと迷いにくくなります。分類ペインやツール画面で、本体ナビの内側へ中央寄せの余白を重ねないかも確認できます。長文の読み幅を制限する場合は、外枠全体ではなく本文など必要な領域へ適用できます。

見出しは同じ製品名を繰り返さず、画面を占有する大見出しや操作を言い直す説明を必要に応じて省けます。個々の部品だけでなく、利用先の本体から開いた状態と単体表示をPC・スマホ幅で比べ、共通ナビで戻る・進む・ホームまで試すと、組み合わせた時だけの問題を見つけやすくなります。独自の見た目や業務上のナビを禁止する規則ではありません。

## スマホの既定例

tasksのように、スマホでは小さなアプリ名と必要な一覧ボタン・設定を約60pxの1段へ収める例を使えます。操作がない場合は空のヘッダーを作る必要はありません。アカウント・分類・更新・追加は業務領域へ置き、内容に早く到達できるようにします。開始画面が一覧なら一覧自体を表示し、背景を覆うドロワーは利用者が開いた時だけにする方法も選べます。テンプレートもスマホで小さな名前を表示する既定例です。デスクトップや特殊用途、好みに合わせた別の構成も選べます。
